# Validex Pilot Validation Workspace

This directory supports local dry runs of the external-validation workflow on a
small number of real candidate tables. A pilot run is a workflow test and is
not sufficient to claim external validation. It does not establish precision,
accuracy, clinical validity, or any other performance claim.

## Repository model

The pilot workspace uses a local-only data model. A clean clone intentionally
contains policy, metadata, templates, notes, and directory scaffolding, but no
private or license-restricted source tables, populated labels, or generated
results. That clean-clone state is complete and valid; the test suite must not
require local pilot data.

Tracked files include:

- `registry.pilot.csv`: candidate metadata and the tracked candidate status.
- `registry.pilot.template.csv`: blank registry structure.
- `labels.pilot.template.csv`: the header-only schema for local labels.
- `notes/`: candidate records, templates, and historical context.
- `tables/.gitkeep`: the tracked anchor for the otherwise local-only table
  directory.
- `results/README.md`: the tracked anchor and policy for the results directory.
- Intake helpers and this README.

Local-only, Git-ignored files include:

- `tables/*.csv`, `tables/*.tsv`, `tables/*.xlsx`, and `tables/*.xls`.
- `labels.pilot.csv`, when a developer creates it from direct inspection of one
  or more local tables.
- Files and nested directories generated by pilot runs under `results/`.

The repository does not track a populated `labels.pilot.csv`. Developers may
create it locally after directly inspecting one or more local pilot tables. It
is optional in a clean clone and in a workspace that has not reached the
labeling step; it is required only when running the validation runner with
local labels.

Repository-policy tests use Git to distinguish tracked scaffolding from ignored
local output. They run in normal source-checkout CI. When the Git executable or
`.git` metadata is unavailable, those tests skip with an explicit reason;
portable package behavior does not depend on Git metadata.

## Candidate eligibility and status

A candidate must satisfy the criteria in
`docs/external_validation_protocol.md`, including being a real post-analysis
result table, having sufficient rows and columns, and being legally accessible
for local review. The `source_type` values are `journal_supplement`,
`repository_record`, `preprint_supplement`, or `other`.

The registry separates run readiness from evidence status.

The `included` field controls whether the validation runner selects a row:

- `pending`: eligibility, provenance, or local inspection remains incomplete.
- `yes`: included for the current local pilot run after the actual local table
  is inspected and eligibility is confirmed.
- `no`: excluded, with a specific `exclusion_reason`.

The `evidence_status` field records the strongest tracked evidence without
claiming more than the repository can support:

- `pending`: the intended result table has not been inspected.
- `locally_inspected`: a tracked note records direct source/header inspection,
  but no attributable local Validex run is established.
- `locally_validated`: a local Validex run is documented and attributable to
  the same candidate. None of the current candidates meets this standard.
- `excluded`: the candidate was explicitly excluded under the pilot protocol.

A source citation or an ignored filename does not prove that a table exists
locally, matches the candidate, or is eligible for a run.

## Local pilot workflow

1. Select a `pending` candidate in `registry.pilot.csv`.
2. Confirm its source, table identity, access terms, and licensing; set
   `included=yes` in the working registry only after the local table satisfies
   the protocol.
3. Download or prepare the candidate table locally without adding restricted or
   copied study data to Git.
4. Place the table under `validation/pilot/tables/` using a supported extension:
   `.csv`, `.tsv`, `.xlsx`, or `.xls`, and record that exact safe basename in
   the working registry's `table_filename` field.
5. Inspect the actual header row, selecting the intended sheet explicitly for a
   workbook and documenting any conversion or cleanup in the candidate note.
6. Copy the header-only `labels.pilot.template.csv` to the ignored local
   `labels.pilot.csv` and record mappings only for tables directly inspected.
7. Run pilot validation with the working registry, local labels, and local
   tables.
8. Save generated outputs under `validation/pilot/results/`.
9. Update the candidate note with the prediction, observed local findings,
   provenance or conversion details, and reproducibility limitations.
10. Do not commit restricted source tables, generated labels, or generated
    results.

For CSV and TSV files, the intake helper can display the header:

```bash
python validation/pilot/inspect_table_headers.py validation/pilot/tables/PILOT_003.tsv
```

The helper can inspect an XLSX workbook when `openpyxl` is available. Otherwise,
convert the selected sheet outside the repository and record that conversion in
the candidate note; do not add a dependency solely for pilot intake.

For each canonical label field (`compound_id`, `effect_size`, `p_value`, `fdr`,
and `annotation`), enter the exact source header, leave it blank when absent, or
serialize multiple defensible candidates as
`AMBIGUOUS:First header|Second header`. Ambiguity is not required: a single
unambiguous annotation header is valid. A genuine effect-size header is also
valid; labels must describe the inspected table rather than reproduce a
historical pattern. Record expected finding codes as a pipe-separated list and
explain required blank mappings in `review_notes`.

Run the local workflow with:

```bash
python validation/run_external_validation.py \
    --registry validation/pilot/registry.pilot.csv \
    --labels validation/pilot/labels.pilot.csv \
    --tables-dir validation/pilot/tables \
    --output validation/pilot/results/pilot_results.json
```

The runner processes only registry rows whose working status is `included=yes`.
Generated output remains local and ignored.

## Licensing and non-redistributable candidates

Do not commit supplementary tables unless the license clearly permits redistribution.

Public access alone does not establish redistribution permission. Record one of
the documented license triage statuses in the registry, keep the table local,
and cite only verifiable source metadata. If a candidate cannot legally be
redistributed, developers may still inspect it locally when its access terms
permit that use, but must not commit the table, generated labels derived from
it, or generated results containing restricted content. If local review is not
permitted or provenance cannot be confirmed, leave the candidate `pending` or
mark it `no` with a specific reason. Never commit patient-identifiable data or
raw instrument files.

## Historical local observations

The candidate notes and `notes/uploaded_table_header_inspection.md` retain
non-sensitive observations from a prior local dry run involving filenames
containing ST000915, ST002843, ST002334, and ST000164. They report a shared
header pattern and an ambiguous annotation mapping. The source tables are not
tracked and are absent from a clean clone. Ignored ST-named files may exist in a
developer workspace, but tracked evidence does not establish that those files
are the same datasets as the original five publication/repository candidates
in the registry. This identity collision remains unresolved.

Treat those entries as manually recorded historical observations only. They do
not prove current file existence, inspection, provenance, mapper output, or
reproducibility, and they must not be copied into a populated label fixture.
Current local labels must be produced from the actual local tables.

## Claim boundary

A local pilot can establish that the workflow ran on the locally available
tables and can reveal possible alias gaps for follow-up. It cannot establish
that Validex has been externally validated or support performance claims. Formal
external validation requires the protocol's sampling, independent review,
reproducible evidence, and scoped reporting requirements.
